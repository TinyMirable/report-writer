# 系统架构图绘制准则


本文件作为系统架构图的绘制标准，智能体在绘图的时候必须先阅读图片[系统架构图例.png](../../assets/系统架构图例.png)，然后再根据下面标准使用drawio绘图：

## 1. 明确受众与视图单一职责：
一张图只讲一件事，不要试图用一张图涵盖业务、技术、部署和数据。

## 2. 标准的层级与模块划分

系统架构图应采用分层架构表达，自上而下展示用户触点、接入层、业务层、基础服务层和数据存储层。

自上而下通常分为：接入层：网关、负载均衡、CDN、反向代理（如 Nginx）。
- 网关与服务层：API 网关、业务微服务。
- 数据与存储层：关系型数据库、NoSQL、缓存（Redis）、消息队列（Kafka）、对象存储。
- 基础设施层：云服务器、容器编排（K8s）、网络安全策略等。

矩阵式扩展用于表达贯穿多层的横切能力，如认证授权、日志、监控、配置管理、异常处理和运维支撑。可将这些能力放在架构图右侧竖条或独立分组中，不要与主业务链路混成同一层。

## 3. 绘制视觉规范
- 定义边界：明确系统的边界，即哪些部分属于系统内部，哪些属于外部依赖。这有助于在视觉上区分系统的核心与外围。
- 识别组件：列出系统的所有主要组件，包括硬件、软件、数据库、网络设备等。每个组件都应在架构图中有一个明确的表示。
- 绘制组件间的交互：使用线条或箭头表示组件之间的数据流、消息传递或依赖关系。确保这些交互关系清晰、准确，易于理解。
- 添加注释和标签：为组件和交互添加必要的注释和标签，以解释其功能、类型或重要性。这有助于读者更快地理解架构图。
- 核心视觉规范色彩克制：整体色彩一般不超过 3 种，使用低饱和度背景区分层级。可使用特定颜色高亮核心链路或第三方服务。
- 形状与线条：组件用矩形框（圆角矩形）。
- 数据库使用特有符号（圆柱体）。线条与箭头代表调用流向（如实线代表强同步调用，虚线代表异步或事件驱动）。
- 图例（Legend）：必须在角落添加图例，解释不同颜色、线条、图标代表的含义。
## 4. 绘制规则
| 规则    | 要求                                                                    |
| ----- | --------------------------------------------------------------------- |
| 分层布局  | 整体采用自上而下布局，按「展示层→接入层→服务层→数据访问层→数据层」排列，不得交叉。                           |
| 容器层级  | 外层使用浅色背景矩形表示 Layer；Layer 内使用虚线框表示 Module；Module 内使用圆角矩形表示 Service。    |
| 数据库表示 | 所有数据库、缓存、消息队列、对象存储均使用圆柱体图标，并标注具体产品名称（如 MySQL、Redis、RabbitMQ、OSS）。     |
| 图标规范  | 前端使用 PC/手机图标；网关使用 Gateway 图标；数据库使用 Cylinder 图标；中间件可使用官方 Logo 或统一组件图标。 |
| 元素命名  | 每个元素必须有明确文字标签，不使用“模块1”“服务A”等无意义名称。                                    |
| 箭头方向  | 主调用链统一自上而下；同步调用使用双向箭头（⇅）或双向连线；依赖关系使用单向箭头（→）。                          |
| 协议标注  | 跨层连接必须在线路旁标注协议或接口形式，如 HTTP(S)、REST API、WebSocket、JDBC、JPA、MQ、S3。      |
| 避免交叉  | 连线尽量保持水平或垂直，不交叉、不穿越模块；必要时调整模块位置或增加留白。                                 |
| 对齐与间距 | 同层组件水平对齐，大小一致，间距均匀；不同层之间保持固定垂直间距。                                     |
| 服务治理  | 注册中心、配置中心、服务发现、链路追踪、日志等治理能力放在服务层侧边或独立治理区域，不与业务服务混排。                   |
| 运维能力  | 日志、监控、权限控制、CI/CD 等横向能力放在右侧竖栏或独立公共能力区。                                 |
| 数据流表达 | 图中应体现完整调用链：客户端 → 网关 → 服务 → 数据访问 → 数据存储；必要时可补充返回路径或异步消息流。              |
| 配色规范  | 同一类别元素保持统一颜色（如前端粉色、接入层浅蓝、服务层浅黄、数据层浅蓝），避免颜色过多导致语义混乱。                   |
| 可读性   | 优先保证信息层次清晰，不为了展示所有技术而堆叠元素；复杂系统可拆分为总架构图 + 子系统架构图。                      |

## 4. Checklist

- 分层架构是否清晰，且每层有明确名称。
- 是否使用 drawio 或 draw.io XML 保存可维护的架构图源文件。
- 系统边界、外部依赖和内部模块是否区分清楚。
- 同层模块尺寸、命名粒度和视觉风格是否一致。
- 是否用低饱和度颜色区分层级，避免装饰性过强。
- 矩阵式扩展能力是否放在右侧竖条或独立分组中。
- 箭头方向是否表达真实调用、数据流或依赖关系。
- 是否避免连线穿过节点、标签重叠和过密布局。
