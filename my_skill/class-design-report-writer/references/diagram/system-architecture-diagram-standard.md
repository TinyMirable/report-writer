
# 系统架构图绘制准则

## 一、整体布局原则

| 原则 | 说明 |
|------|------|
| **分层架构** | 采用自上而下的横向分层设计，常见层级：前端应用 → 接入层 → 网关层 → 业务中台 → 基础服务 → 数据存储层 |
| **矩阵式扩展** | 支持纵向贯穿式辅助模块（如日志、权限、运维、监控），以竖条形式置于右侧 |
| **对齐规范** | 同层模块顶部对齐，层间保持等距间距；整体居中对齐或左对齐 |
| **留白比例** | 层间间距 ≥ 模块高度的 50%，模块间横向间距 ≥ 模块宽度的 30% |

---

### 二、分层与配色规范

每层使用**独立背景色**进行视觉区分，颜色遵循"上浅下深"或"按功能域区分"原则：

| 层级 | 推荐背景色 | 文字色 | 用途 |
|------|-----------|--------|------|
| 前端应用 | 浅粉/浅橙 | 深蓝/深灰 | 用户触点 |
| 服务接入 | 浅蓝 | 深灰 | 网络加速、负载均衡 |
| API接口/网关 | 橙黄/琥珀 | 深灰/黑 | 统一认证、路由 |
| 服务中台 | 淡紫/浅蓝 | 深灰 | 核心业务逻辑 |
| 公共基础服务 | 浅绿/薄荷 | 深灰 | 通用能力（日志、文件、消息） |
| 数据存储层 | 浅橙/米黄 | 深灰 | 持久化存储 |
| 运维/监控 | 浅灰/浅绿 | 深灰 | 贯穿全栈的辅助能力 |

> **注意**：背景色使用低饱和度（ pastel 色系），透明度建议 15%-30%，避免喧宾夺主。

---

### 三、模块绘制规范

#### 3.1 标准模块
- **形状**：圆角矩形（圆角半径 4-8px）或直角矩形
- **边框**：1px 实线，颜色比背景色深 20%，或无边框（依赖背景色区分）
- **填充**：白色或极浅色填充，确保文字清晰可读
- **尺寸**：宽度 100-160px，高度 40-60px（保持同层一致）
- **阴影**：不使用阴影，保持扁平化风格

#### 3.2 模块分组
- 同一业务域的模块用**虚线框**或**同色浅背景**包裹
- 分组标题置于框顶部居中，字号比模块文字小 1-2pt，颜色略浅

#### 3.3 图标使用
- 每个关键模块可配一个**扁平化图标**（16×16 或 24×24）
- 图标置于模块内文字上方或左侧
- 图标风格统一（线框型或填充型，不可混用）

---

### 四、文字标注规范

| 元素 | 字体 | 字号 | 颜色 | 位置 |
|------|------|------|------|------|
| 层级标题 | 黑体/思源黑体 | 14-16pt | 深蓝（#2B5F9A） | 该层左侧，垂直居中 |
| 模块名称 | 黑体/微软雅黑 | 11-13pt | 深灰（#333333） | 模块内居中 |
| 分组标题 | 黑体 | 12-14pt | 深灰/黑色 | 分组框顶部居中 |
| 补充说明 | 宋体/等线 | 9-10pt | 中灰（#666666） | 模块下方或括号内 |

---

### 五、纵向贯穿服务表示法

对于日志、权限、运维等**跨层服务**：

1. **位置**：置于架构图最右侧
2. **形式**：窄竖条矩形，高度贯穿多个层级
3. **背景**：与对应功能域同色（如运维用绿色系）
4. **文字**：竖排文字或 90° 旋转文字，置于条带中央
5. **边界**：用虚线或细实线与其他层级分隔

---

### 六、连线与关系

| 关系类型 | 表示方式 |
|----------|----------|
| 数据流向 | 使用单向箭头，颜色为深蓝或灰色，线宽 1-2px |
| 依赖关系 | 使用虚线箭头 |
| 双向通信 | 使用双向箭头或无箭头实线 |
| 层级边界 | 不使用连线，依靠背景色和间距自然区分 |

> **简化原则**：若层级关系明确（自上而下），可省略大部分连线，仅用背景分层暗示流向。

---

### 七、输出格式建议

使用 D2（Declarative Diagramming） 绘制系统架构图

---

### 绘制要点
定义边界：明确系统的边界，即哪些部分属于系统内部，哪些属于外部依赖。这有助于在视觉上区分系统的核心与外围。

识别组件：列出系统的所有主要组件，包括硬件、软件、数据库、网络设备等。每个组件都应在架构图中有一个明确的表示。

绘制组件间的交互：使用线条或箭头表示组件之间的数据流、消息传递或依赖关系。确保这些交互关系清晰、准确，易于理解。

添加注释和标签：为组件和交互添加必要的注释和标签，以解释其功能、类型或重要性。这有助于读者更快地理解架构图。

在完成基础的系统架构图后，可以合理利用颜色和图标增强架构图的视觉效果，使其更加生动、易于理解，比如使用不同的颜色区分不同类型的组件，或使用图标表示特定的技术或协议。尽管系统架构图需要包含足够的信息以支持决策，但也要避免过于复杂和冗余。保持简洁有助于读者快速抓住重点，理解系统结构。
### 八、Checklist（绘制后自检）

- [ ] 分层是否清晰？每层是否有明确的层级标题？
- [ ] 同层模块尺寸是否一致？间距是否均匀？
- [ ] 背景色是否区分明显且不过于鲜艳？
- [ ] 文字是否在所有模块内清晰可读？
- [ ] 跨层服务是否以竖条形式正确贯穿？
- [ ] 是否避免了交叉连线和过度装饰？
- [ ] 整体风格是否扁平、专业、简洁？

### 九、示例分层模板（可直接套用）

```
┌─────────────────────────────────────────┐
│  [前端应用]  APP | 小程序 | PC端 | API客户端 │
├─────────────────────────────────────────┤
│  [服务接入]  CDN加速        负载均衡        │
├─────────────────────────────────────────┤
│  [API网关]  统一认证 | 限流 | 路由          │
├─────────────────────────────────────────┤
│  [服务中台]  用户中心 | 订单中心 | 支付中心   │
├─────────────────────────────────────────┤
│  [基础服务]  日志 | 文件 | 消息 | 缓存        │
├─────────────────────────────────────────┤
│  [数据层]   MySQL | Redis | MQ | OSS        │
└─────────────────────────────────────────┘
           ↑ 日志 ↑ 监控 ↑ 运维（右侧竖条）
```
